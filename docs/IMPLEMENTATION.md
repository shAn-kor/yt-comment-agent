# 기능별 구현 설명

이 문서는 대시보드의 각 기능이 코드에서 어떻게 동작하는지 설명한다. 실행 방법은 [README](../README.md)에 있다.

## 한눈에 보기

```
브라우저 화면 (public/)  HTML · CSS · 순수 JavaScript
   │  fetch
   ▼
FastAPI 서버 agent/server.py  ──  127.0.0.1:4310, 내 컴퓨터에서만 접속
   ├─ 영상 자료     agent/youtube.py   yt-dlp 라이브러리
   ├─ 초안 생성     agent/generate.py  → agent/llm.py (Claude · Gemini · Groq · OpenRouter)
   ├─ 댓글 검사     agent/validate.py
   ├─ 운영 규칙     agent/rules.py
   ├─ 기록 저장     agent/store.py     SQLite (data/agent.db)
   └─ 게시          agent/poster.py    Playwright + 내 크롬 프로필
```

| 부분        | 쓴 것                                      |
| ----------- | ------------------------------------------ |
| 언어        | Python 3.11 이상 (서버), JavaScript (화면) |
| 서버        | FastAPI + Uvicorn                          |
| 영상 자료   | yt-dlp (Python 라이브러리로 직접 호출)     |
| 크롬 조작   | Playwright (async API)                     |
| 기록        | Python 내장 `sqlite3`                      |
| 설정        | PyYAML                                     |
| 테스트      | pytest, FastAPI `TestClient`               |
| 패키지 관리 | uv (`pyproject.toml`, `uv.lock`)           |

원칙은 하나다. **규칙은 화면이 아니라 서버가 강제한다.** 화면에서 버튼을 막는 것은 안내용이다. 실제 차단은 게시 직전에 서버가 다시 검사해서 한다.

처음에는 Node.js로 만들었다가 FastAPI로 옮겼다. API 주소와 응답 모양을 그대로 유지해서 화면 코드는 바꾸지 않았다. yt-dlp가 원래 Python 프로그램이라 외부 프로그램으로 실행하지 않고 코드에서 바로 부를 수 있게 된 점이 가장 큰 이득이다.

## 1. 설정 — `config.yaml`, `agent/config.py`

바꿀 수 있는 값은 모두 `config.yaml` 한 곳에 둔다.

| 항목            | 내용                                                                    |
| --------------- | ----------------------------------------------------------------------- |
| `profiles`      | 크롬 프로필 3개 (유튜브1~3)와 폴더 위치                                 |
| `channels`      | 허용 채널 5곳의 채널 ID와 이름                                          |
| `test_videos`   | 본인 테스트 영상 ID                                                     |
| `posting_scope` | `test_only`(기본): 테스트 영상에만 게시. `channels`: 지정 채널에도 게시 |
| `comment`       | 40~120자, 브랜드 이름 "운명원"                                          |
| `limits`        | 하루 10개, 채널당 영상 5개                                              |
| `rising`        | 뜨기 직전 영상의 기준 (검색어, 조회수 범위, 시간당 조회수)              |

`load_config()`는 설정을 dataclass로 읽고, 빠진 값은 기본값으로 채운다. `posting_scope`에 이상한 값이 들어가면 안전한 쪽인 `test_only`로 본다. `load_env()`는 `.env` 파일에서 API 키 같은 값을 읽는다. 이미 환경 변수에 있는 값은 덮어쓰지 않는다.

## 2. 영상 불러오기 — `agent/youtube.py`

**YouTube Data API 키 없이** 동작하게 만들었다. 모든 함수는 블로킹 함수이고, 서버가 `asyncio.to_thread`로 스레드에서 부른다. 그래서 영상 자료를 받는 동안에도 다른 요청을 처리할 수 있다.

- **채널 최신 영상** `fetch_channel_feed()`: 채널마다 최근 5개를 가져온다. 두 가지 방법을 차례로 쓴다.
  1. **채널 RSS** (`_rss_feed`): 유튜브가 공개하는 `/feeds/videos.xml?channel_id=…`를 읽는다. 올린 시각이 분 단위로 정확하다. 가끔 404·500을 내지만 다시 요청하면 대개 된다. 그래서 0.5초 쉬고 최대 3번까지 요청한다.
     - 라이브 다시보기(제목이 `Live streaming of`로 시작)는 뺀다. 자막이 없어서 영상 속 장면을 짚기 어렵기 때문이다.
  2. **'동영상' 탭** (`_tab_feed`): RSS가 3번 모두 실패하면 그 채널만 yt-dlp로 채널 '동영상' 탭을 읽는다. 한국어 화면으로 받아야 제목이 원래 한국어로 오고, 영어 화면으로 받아야 yt-dlp가 "3 days ago" 같은 표시에서 날짜와 조회수를 계산할 수 있다. 그래서 두 번 읽어 합친다. 올린 날짜는 날짜 단위 근삿값이다.
  - 영상마다 어느 방법으로 받았는지 `via`(`rss` 또는 `tab`)에 적는다. 화면은 '동영상' 탭으로 받은 채널을 "날짜 어림값"으로 알려 준다.
  - 서킷 브레이커(계속 실패하면 한동안 요청을 끊는 장치)는 넣지 않았다. 버튼 한 번에 요청이 5번뿐이고, 실패도 잠깐씩이라 끊어서 보호할 부담이 없다. 자동으로 자주 돌리게 되면 "RSS가 계속 실패하면 10분 동안 건너뛰기"를 넣으면 된다.
- **5개 채널 동시 요청** (`POST /api/videos`): `asyncio.gather(..., return_exceptions=True)`를 써서 한 채널이 실패해도 나머지는 보여 준다. 실패한 채널은 화면에 이름을 알려 준다.
- **영상 자료** `get_video_context()`: yt-dlp `extract_info`로 제목, 설명, 채널 ID, 조회수, 올린 시각을 받는다.
  - 자막: 사람이 단 한국어 자막을 먼저 찾고, 없으면 자동 자막을 쓴다. `json3` 형식을 받아 글자만 이어 붙인다. 자막이 아예 없으면 제목과 설명만 쓴다.
  - 인기 댓글: `comment_sort=top`으로 40개를 받아 답글을 빼고, 좋아요 순으로 20개를 남긴다.
  - 같은 영상을 다시 열 때 기다리지 않도록 서버가 메모리에 보관한다 (`contexts` 딕셔너리).
- **링크 직접 입력** `parse_video_id()`: `youtu.be/…`, `watch?v=…`, `shorts/…`, `live/…`, 11자리 ID를 모두 받는다. 그다음 서버가 yt-dlp로 **실제 채널 ID를 확인**하고 허용 채널인지 본다. 허용 밖이면 차단하고 기록에 남긴다.

## 3. 뜨기 직전 영상 찾기 — `find_rising()`

1. 유튜브 검색 결과 페이지를 "오늘 업로드" 필터(`sp=EgIIAg==`)로 연다. 검색어는 "연애"다. yt-dlp의 `ytsearchdate`는 지금 버전(2026.08.19)에서 지원하지 않아 이 방법을 쓴다.
2. 30개 중 조회수 1,000~5,000인 영상만 남긴다.
3. 남은 영상의 정확한 업로드 시각을 4개씩 동시에 조회한다 (`ThreadPoolExecutor(4)`).
4. 시간당 조회수 = 조회수 ÷ 올린 뒤 지난 시간. 150 이상만 보여 준다. 방금 올린 영상의 숫자가 과하게 커지지 않도록 지난 시간은 최소 15분으로 계산한다.

이 영상들은 지정 채널이 아닐 수 있다. 그래서 **초안까지만** 만든다. 서버는 이 영상 ID를 `rising_ids`에 기억했다가, 게시 요청이 오면 막고 기록에 남긴다.

## 4. 댓글 초안 생성 — `agent/generate.py`, `agent/llm.py`

### AI 연결 (`llm.py`)

심사자가 Claude 계정이나 유료 키 없이도 돌려 볼 수 있게 무료 모델을 붙였다. 초안 생성 코드(`generate.py`)는 `complete(prompt) -> str` 하나만 부른다. 어느 AI를 쓰든 이 모양은 같다.

**고르는 순서 (`provider_name`)**

1. `.env`의 `LLM_PROVIDER`가 있으면 그 값을 쓴다. 목록에 없는 값이면 오류를 낸다. 화면 위쪽에도 "설정 오류"가 보인다.
2. 비어 있으면 키를 찾는다: `ANTHROPIC_API_KEY` → `GEMINI_API_KEY` → `GROQ_API_KEY` → `OPENROUTER_API_KEY`.
3. 키가 없으면 설치된 `claude` CLI를 쓴다. 기존 사용자는 설정을 바꾸지 않아도 전과 같이 동작한다.
4. 그것도 없으면 Gemini를 고른다. 키가 없으므로 요청을 보내지 않고 "무료 키는 aistudio.google.com/apikey에서 받는다"는 오류를 보여 준다.

**공급자별 연결**

| 공급자     | 주소                                              | 기본 모델                    | 무료 범위 (2026-10-20 공식 문서)                        |
| ---------- | ------------------------------------------------- | ---------------------------- | ------------------------------------------------------- |
| Gemini     | `generativelanguage.googleapis.com/v1beta/openai` | `gemini-3.8-flash`           | 무료 등급에서 입력·출력 무료. 한도는 AI Studio에서 확인 |
| Groq       | `api.groq.com/openai/v1`                          | `openai/gpt-oss-120b`        | 분당 30회, 하루 1,000회, 분당 8,000토큰                 |
| OpenRouter | `openrouter.ai/api/v1`                            | `google/gemma-4-31b-it:free` | 이름이 `:free`로 끝나는 모델. 분당·하루 요청 수 제한    |
| Claude     | `api.anthropic.com/v1/messages` 또는 `claude -p`  | `claude-sonnet-5-5`          | 무료 아님                                               |

- Gemini, Groq, OpenRouter는 모두 OpenAI의 `/chat/completions` 형식을 받는다. 그래서 요청 코드 하나(`_openai_compatible`)를 같이 쓰고 주소, 키 이름, 기본 모델만 표(`OPENAI_COMPATIBLE`)로 나눈다. 새 공급자도 표에 한 줄을 더하면 된다.
- 시간 제한은 API 120초, `claude` CLI 180초다.
- 오류는 화면에서 바로 이해할 수 있는 말로 바꾼다. 키가 없으면 "`.env`에 `GEMINI_API_KEY`가 없음"과 키 발급 주소, 429면 "무료 한도 초과일 수 있음"을 붙인다.
- `claude` CLI는 임시 폴더에서 실행한다. 프로젝트 폴더에서 실행하면 그 폴더의 지침 파일을 읽어서 답이 흔들리기 때문이다.
- 화면 위쪽의 "AI · …" 표시는 `backend_name()`이 정한다. 예: `Gemini · gemini-3.8-flash`.

Ollama 같은 로컬 모델은 넣지 않았다. 심사자 컴퓨터마다 성능이 달라 초안 시간이 들쭉날쭉하고, 모델 파일(약 8GB)을 받아야 해서 "바로 실행해 보기"에 맞지 않기 때문이다.

JSON 모드(`response_format`)는 쓰지 않았다. 공급자와 모델마다 지원 여부가 다르기 때문이다. 대신 `parse_json()`이 답에서 `{ … }`만 꺼내고, 실패하면 다시 요청한다 (아래 "검사 후 다시 쓰기").

**무료 모델로 실제 영상 확인 (2026-10-20, Gemini 무료 등급 `gemini-3.8-flash`)**

서버의 `POST /api/draft`와 같은 순서(`get_video_context` → `draft_comment`)로 지정 채널 영상 2개를 돌렸다. 두 번째 영상은 첫 번째 초안을 "이미 쓴 댓글"로 넣고 돌렸다.

| 영상                                                                    | 자료      | 시도 | AI 응답 시간 | 결과         |
| ----------------------------------------------------------------------- | --------- | ---- | ------------ | ------------ |
| 외롭여 · 서운함 많은 여자들이 꼭 알아야 할 것 (`k_0c0m0Hk5k`)           | 자동 자막 | 1번  | 91초         | 통과 (104자) |
| 심리조각 · 좋아하는 사람 앞에서 말문이 막히는 진짜 이유 (`c-QzU4kuu90`) | 자동 자막 | 1번  | 25초         | 통과 (92자)  |

- 두 답 모두 JSON만 돌려줘서 `parse_json()`이 바로 읽었다. 다시 쓰기는 일어나지 않았다.
- 두 번째 초안의 `detail`은 "머릿속에 하해져요"다. 자동 자막의 오타("하얘져요")를 그대로 가져왔다. 검사기는 "자막에 있는 그대로"를 요구하므로 통과지만, 읽는 사람에게는 오타로 보인다. 사람이 고치면 6글자 연속 겹침 규칙으로 다시 검사된다.
- 응답 시간은 같은 모델에서도 25~91초로 차이가 컸다. 무료 등급이라 대기 시간이 고르지 않을 수 있다.
- Groq, OpenRouter는 요청 형식만 테스트로 확인했다. 실제 초안은 돌려 보지 않았다.

### 프롬프트 (`build_prompt`)

AI에게 "방금 영상을 끝까지 본 한국인 시청자"라는 역할을 주고, 두 단계로 답하게 한다.

1. `concern`: 영상이 다루는 연애 고민 한 줄 (40자 이내)
2. `comment`: 시청자로서 남길 댓글

그리고 `detail`도 함께 받는다. 댓글에서 짚은 영상 속 말을 자막에 있는 그대로 5~15자 적게 한다. 이 값은 나중에 검사기가 "정말 영상에 있는 말인지" 대조하는 데 쓴다.

AI에게 주는 자료는 제목, 채널, 설명, 자막 앞 7,000자, 인기 댓글 20개, 이미 쓴 댓글 10개다. 답은 JSON 하나로만 받는다. `parse_json()`은 앞뒤에 다른 말이 붙어도 `{ … }` 부분만 꺼낸다.

### 검사 후 다시 쓰기 (`draft_comment`)

```
AI 초안 → 검사기 → 통과? ── 예 → 화면으로
                     └ 아니오 → 떨어진 이유를 프롬프트 끝에 붙여 다시 요청 (최대 3번)
```

예를 들어 "글자 수 132자 (기준 40~120자)"라는 이유를 붙이면, 다음 시도에서 AI가 길이를 줄인다. 3번 모두 떨어지면 마지막 초안과 실패 이유를 그대로 보여 준다. 사람이 고칠 수 있게 하기 위해서다. AI가 JSON이 아닌 답을 하면 "JSON 형식으로만 답할 것"을 붙여 다시 요청한다.

## 5. 댓글 검사기 — `agent/validate.py`

AI가 쓴 초안과 사람이 고친 글이 **같은 검사기**를 지난다. 결과는 규칙마다 `{key, label, ok, note}`로 돌려준다. 화면은 이 값으로 ✓/✕ 표를 그린다.

| 규칙                    | 검사 방법                                                                                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 40~120자                | 앞뒤 공백을 빼고 글자 수(코드 포인트)를 센다. 한글과 이모지는 한 글자다                                                                                        |
| "운명원" 한 번          | `text.count(brand)`로 센다. 0번이나 2번 이상이면 실패                                                                                                          |
| 링크·해시태그 없음      | 글을 NFKC로 바꾼 뒤(전각 `ｗｗｗ．`·`＃`도 잡는다) `http`, `www.`, 도메인(`umw.com`, `umw . com`, `사주.한국`), 말로 쓴 도메인(`umw 닷 com`), `#글자`를 찾는다 |
| 이용 후기처럼 쓰지 않음 | "봤는데", "해봤던", "맞더라", "후기", "강추" 같은 말을 **"운명원"이 들어간 문장에서** 찾는다. 영상 이야기를 하며 "영상 봤는데"라고 쓰는 것은 괜찮기 때문이다. 다만 "사주 봤는데"처럼 사주·타로·궁합을 본 경험담은 문장과 상관없이 막는다 |
| 영상 속 장면·말 포함    | 아래 설명                                                                                                                                                      |
| 이전 댓글과 다름        | 아래 설명                                                                                                                                                      |

**영상 속 장면·말 확인.** 유니코드 정규화(NFC) 후 소문자로 바꾸고 글자·숫자만 남겨 비교한다 (`norm`). 둘 중 하나면 통과다.

- AI가 밝힌 `detail`(5글자 이상)이 자막·제목·설명에도 있고 댓글에도 있다. `detail`은 화면이 보내는 값이라 "오늘은" 같은 흔한 짧은 말로 통과하지 못하게 길이를 본다.
- 또는 댓글과 영상 자료가 6글자 이상 연속으로 겹친다 (`longest_common`). 브랜드 이름은 빼고 비교한다. 사람이 고친 글은 `detail`과 달라질 수 있어서 이 방법을 하나 더 두었다.

찾은 부분은 `_locate()`로 원래 댓글에서 다시 찾아 `anchor`로 돌려준다. 화면 미리보기는 이 부분을 색으로 강조한다.

**이전 댓글과 비교.** 두 글을 두 글자씩 잘라 겹치는 비율을 잰다 (bigram Jaccard). 0.5 이상이면 너무 비슷하다고 본다. 비교 대상은 **다른 영상**에 단 댓글과 초안이다. 같은 영상의 초안을 조금 고친 글은 당연히 비슷하므로 뺀다.

옮기면서 Node 버전과 결과가 같은지 대조했다. 통과, 브랜드 2번, 링크, 후기, 전각 문자·이모지가 섞인 문장 5개에서 `ok`, 오류 문구, 글자 수, `anchor`, `checks`가 모두 같았다.

## 6. 운영 규칙 — `agent/rules.py`

| 함수               | 하는 일                                                                                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check_load_scope` | 초안까지 허용되는 영상인가: 허용 채널 영상 또는 본인 테스트 영상                                                                                              |
| `check_post_scope` | 게시가 허용되는 영상인가: `test_only`면 테스트 영상만                                                                                                         |
| `check_post`       | 게시 직전 최종 검사: 설정에 있는 프로필인가 → 게시 범위 → 이 영상에 이미 게시된 댓글이 있는가 (계정과 상관없이 영상당 1개) → 오늘 게시가 10개 미만인가 → 로그인된 프로필인가. "게시됨"은 `success`와 `unverified`를 함께 센다 |
| `pick_profile`     | 자동 배정: 로그인된 계정 중 가장 오래 안 쓴 계정을 고른다                                                                                                    |
| `kst_date`         | "오늘"을 한국 시간 기준 날짜로 계산한다                                                                                                                       |

채널 확인에는 화면이 보낸 값을 쓰지 않는다. 서버가 yt-dlp로 받은 채널 ID로만 판단한다. 화면 요청을 조작해도 허용 밖 채널에 게시할 수 없다.

영상 ID도 11자리 형식(`[A-Za-z0-9_-]`)만 받는다. 예전에는 `ID&t=1`처럼 뒤에 무언가 붙인 값을 다른 영상으로 보고 영상당 1개 검사를 통과시켰다. yt-dlp가 돌려준 ID가 요청한 ID와 다르면 영상 자료를 쓰지 않는다.

**로그인된 프로필.** `scripts/login.py`가 프로필 폴더에 `.agent-login` 표시를 남긴다. 서버는 이 표시가 있고, 그 시각 뒤에 "로그인 안 됨"으로 실패한 기록이 없는 프로필만 준비된 것으로 본다. 자동 배정도 이 프로필 중에서만 고른다. 로그인 안 된 계정이 자동 배정되어 시연 중 실패하는 일을 막는다. 다시 로그인하면 표시 시각이 바뀌어 다시 준비됨이 된다.

## 7. 기록 — `agent/store.py`

SQLite 파일(`data/agent.db`)의 `logs` 표 하나에 모든 시도를 남긴다. Node 버전과 표 구조가 같아서 옛 기록도 그대로 읽는다.

- 칸: 시각(밀리초), 날짜(한국 시간), 영상, 채널, 계정, 댓글, 결과, 이유, 캡처 파일, 댓글 링크
- 결과는 네 가지다.
  - `success`: 게시하고 내 댓글까지 확인함
  - `unverified`: 게시 버튼은 눌렀지만 내 댓글을 확인하지 못함. 새 계정 댓글은 스팸 필터에 숨겨질 수 있어 실제로는 올라갔을 수 있다. 그래서 영상당 1개와 하루 상한에서 게시된 것으로 센다
  - `failed`: 게시 버튼을 누르기 전에 실패함 (로그인 안 됨, 댓글창 없음 등)
  - `blocked`: 규칙에 걸려 시도하지 않음 (허용 밖 링크, 검사 실패, 영상당 1개, 하루 상한)
- 규칙 검사도 이 표를 쓴다. "이 영상에 성공 기록이 있나", "오늘 성공이 몇 개인가"를 바로 조회한다. 서버를 껐다 켜도 규칙이 유지된다.
- FastAPI는 요청을 여러 스레드에서 처리하므로 연결 하나를 잠금(`threading.Lock`)과 함께 쓴다.

## 8. 게시 — `agent/poster.py`, `scripts/login.py`

### 로그인 (`uv run python scripts/login.py 유튜브1`)

프로필 폴더를 지정해(`--user-data-dir`) **일반 크롬**을 연다. 사람이 직접 구글에 로그인하고 창을 닫으면 로그인 상태가 그 폴더에 남는다. 자동 조작 창에서는 구글이 로그인을 막는 경우가 있어서 이렇게 나눴다.

### 게시 순서 (`post_comment`)

1. Playwright `launch_persistent_context`로 그 프로필 폴더를 쓰는 크롬을 **화면에 띄운다**. 시연 영상에서 실제 입력이 보이게 하기 위해서다.
2. 영상을 한국어 화면(`hl=ko`)으로 연다. 로그인 버튼이 보이면 "로그인 안 됨"으로 멈춘다.
3. 댓글창이 나올 때까지 아래로 조금씩 스크롤한다 (최대 15번). "댓글 사용 중지" 안내가 보이면 멈춘다.
4. 입력창을 누르고 **한 글자씩** 입력한다. 글자 사이에 60~170ms를 무작위로 쉰다.
5. 게시 버튼을 누른다.
6. 댓글 목록에서 **내 댓글 앞 18자가 들어간 댓글**이 20초 안에 보이는지 확인한다. 보이면 그 댓글의 링크를 가져오고 화면을 캡처한다.

어느 단계에서 실패하든 그 순간 화면을 `data/shots/`에 캡처하고 기록에 붙인다. 시연 영상에서 결과를 볼 수 있도록 성공 후 2.5초 기다렸다가 창을 닫는다.

### 진행 상태 전달

게시는 30초 넘게 걸릴 수 있다. 그래서 서버는 게시를 `asyncio.create_task`로 뒤에서 돌리고 작업 번호(`jobId`)를 바로 돌려준다. 게시 코드는 단계가 바뀔 때마다 상태 글자를 바꾸고("댓글창 찾는 중", "입력 중" …), 화면은 0.6초마다 `GET /api/job`으로 상태를 물어 진행 목록을 갱신한다.

한 번에 하나만 게시한다 (`busy` 플래그). 게시 중에 다시 누르면 409로 거절한다.

## 9. 서버 — `agent/server.py`

FastAPI 앱이다. 요청 본문은 Pydantic 모델(`ResolveIn`, `DraftIn`, `ValidateIn`, `PostIn`)로 받는다. 오류는 화면이 기대하는 `{"error": "..."}` 모양으로 돌려준다 (`ApiError` 예외 처리기).

| API                   | 하는 일                                                 |
| --------------------- | ------------------------------------------------------- |
| `GET /api/config`     | 계정 준비 상태, 게시 범위, 오늘 사용량, AI 종류         |
| `POST /api/videos`    | 5개 채널 최신 영상                                      |
| `POST /api/resolve`   | 링크 → 영상 ID → 채널 확인. 허용 밖이면 403과 차단 기록 |
| `POST /api/draft`     | 고민 한 줄, 초안, 검사 결과, 게시 전 확인 결과          |
| `POST /api/validate`  | 사람이 고친 글을 다시 검사                              |
| `POST /api/post`      | 최종 검사 후 게시 시작                                  |
| `GET /api/job`        | 게시 진행 상태                                          |
| `GET /api/post-state` | 게시 전 확인 (범위, 영상당 1개, 오늘 남은 개수)         |
| `GET /api/logs`       | 기록 최근 200개                                         |
| `POST /api/rising`    | 뜨기 직전 영상                                          |

**`POST /api/post`가 게시 전에 확인하는 순서**

1. 뜨기 직전 영상인가 → 403 차단
2. 댓글 검사기를 **다시** 돌림 → 실패하면 422 차단
3. `check_post` (계정, 게시 범위, 영상당 1개, 하루 상한) → 실패하면 403 차단

차단될 때마다 이유와 함께 기록에 남긴다.

안전장치도 몇 가지 넣었다.

- 서버는 `127.0.0.1`에서만 열린다. 같은 와이파이의 다른 기기는 접속할 수 없다.
- 요청의 `Host`가 `localhost`·`127.0.0.1`이 아니거나, `Origin`이 다른 사이트면 403으로 막는다 (`local_only`). 내 브라우저에서 연 다른 웹사이트가 DNS 리바인딩으로 대시보드를 조종하는 것을 막는다.
- 게시 요청이 오면 검사를 시작하기 전에 "게시 중"으로 잠근다. 영상 자료를 받는 동안 두 번째 요청이 끼어들어 같은 영상에 두 번 게시하지 못한다.
- 없는 프로필 폴더로는 Chrome을 열지 않는다. 열면 빈 프로필이 생겨 로그인한 것처럼 보이기 때문이다.
- 화면 파일(`public/`)과 캡처 파일(`/shots`)은 FastAPI `StaticFiles`로 준다. `../`나 `%2e%2e`로 다른 폴더의 파일을 읽을 수 없다 (테스트로 확인).
- Playwright는 게시할 때만 불러온다. 서버 시작이 빠르고, 크롬이 없어도 초안까지는 쓸 수 있다.

## 10. 화면 — `public/`

빌드 도구 없이 HTML, CSS, 순수 JavaScript로 만들었다. 서버를 켜면 바로 열린다.

- **세 칸 구조**: ① 영상 불러오기 → ② 영상 선택 → ③ 댓글 달기. 각 칸 제목 옆에 "완료 / 지금 / 대기"를 표시한다 (`renderSteps`). 맨 위 단계 표시도 같은 값을 쓴다.
- **초안 편집**: 글을 고치면 0.3초 뒤에 `/api/validate`로 다시 검사한다. 글자 수 막대는 40~120자 구간과 현재 위치를 보여 준다.
- **규칙 검사표**: 검사기의 `checks`로 ✓/✕를 그리고, 떨어진 규칙은 아래에 이유를 글로 적는다. 색을 구분하기 어려운 사람도 알 수 있게 하기 위해서다.
- **미리보기**: 유튜브 댓글 모양으로 보여 준다. 검사기가 돌려준 `anchor`(영상에서 가져온 말)는 배경색으로, "운명원"은 글자색으로 강조한다.
- **게시 전 확인**: 댓글 검사 통과 여부와 `/api/post-state`의 세 항목을 보여 준다. 하나라도 ✕면 "댓글 달기" 버튼이 꺼진다.
- **기록 표**: 전체 / 성공 / 확인 안 됨 / 실패 / 차단으로 거를 수 있다. 차단과 실패는 이유를 함께 보여 준다.
- **디자인**: macOS 최신 디자인을 따랐다. 위쪽 막대와 왼쪽 목록은 반투명이고, 색은 시스템 파랑 하나와 성공·실패 색만 쓴다. 컴퓨터가 다크 모드면 자동으로 어두워진다 (`prefers-color-scheme`).
- **오류 상황 처리** (사용자 검토 2026-10-20):
  - 게시 중에는 다른 영상을 고를 수 없다. 결과는 게시한 영상에 붙는다 (`state.posting`, `markCommented`).
  - 게시 전 확인에 계정 항목을 넣었다. 자동 배정인데 로그인된 계정이 없으면 "로그인된 계정 없음"으로 보인다. 창으로 돌아오면 설정을 다시 읽는다.
  - 글을 고치는 동안에는 "댓글 달기" 버튼이 꺼진다. 재검사가 실패하면 검사표를 ✕로 둔다. 늦게 온 옛 응답은 버린다 (`checkSeq`).
  - 오류 문구는 한국어로 보여 준다. 서버 연결 실패는 "서버에 연결할 수 없습니다…", yt-dlp 오류는 "영상 정보를 가져오지 못함: …".
  - 링크가 차단되면 기록 표를 바로 새로 고친다.
  - 초안 생성이 60초를 넘기면 늦어진다는 안내를, 시간 초과·사용량 초과면 해결 방법을 보여 준다.
  - 앞서 고른 영상의 오류가 지금 영상 화면을 덮어쓰지 않는다.
  - 불러오기와 뜨기 직전 찾기는 하나가 도는 동안 둘 다 꺼진다.

## 11. 테스트 — `tests/`

`uv run pytest`로 63개를 돌린다. 외부 서비스 없이 돌아가도록 AI는 가짜 함수나 가짜 HTTP 응답으로, 영상 자료와 기록 저장소는 테스트용으로 바꿔 끼운다.

- `test_validate.py`: 통과 예시, 글자 수, 브랜드 0번·2번, 링크·해시태그, 후기 표현, 브랜드 없는 문장의 "봤는데" 허용, 영상 속 말 확인, 유사도, 강조 부분이 원문 그대로인지
- `test_llm.py`: 공급자 고르는 순서 (`LLM_PROVIDER` 우선, 키, `claude` CLI, 아무것도 없으면 Gemini 키 안내), 공급자별 주소·키·기본 모델, 키 없음·429·Gemini 목록형 오류·빈 답 처리
- `test_generate.py`: JSON 꺼내기, 실패 이유를 붙여 다시 쓰는지, JSON이 아닌 답이면 다시 요청하는지
- `test_rules.py`: 허용 채널, 테스트 모드, 설정에 없는 계정 차단, 영상당 1개, 하루 상한(다음 날 풀림), 비교용 이전 댓글에서 같은 영상 제외, 계정 자동 배정, 한국 시간 날짜. 기록은 임시 폴더의 SQLite로 확인한다.
- `test_youtube.py`: 링크에서 영상 ID 꺼내기, RSS 읽기(정확한 시각, 라이브 제외), 실패하면 다시 요청, 계속 실패하면 '동영상' 탭으로 넘어가기, 둘 다 실패하면 두 이유를 함께 알리기, yt-dlp 오류를 한국어 문구로 바꾸기
- `test_server.py`: 설정과 화면 파일, 허용 밖 링크 차단과 기록, 설정의 채널 이름 사용, 고친 글 재검사, 테스트 모드의 게시 차단과 게시 전 확인 항목, 검사에 떨어진 글 차단, 경로 탈출 차단
- `test_attacks.py`: 레드팀 검토(2026-10-20)에서 찾은 우회 방법. 모양을 바꾼 링크·해시태그, 후기 우회, 흔한 짧은 인용구, 영상 ID 변형, 다른 주소의 요청, 확인 안 된 게시, 로그인 안 된 프로필, 동시 게시. 고치기 전 코드에서는 19개 중 18개가 실패한다 (나머지 1개는 평범한 문장을 링크로 오인하지 않는지 보는 테스트)

## 아직 확인하지 못한 것

- **실제 게시**: 로그인한 테스트 계정과 테스트 영상이 아직 없다. 유튜브 화면 구조가 바뀌었다면 `poster.py`의 선택자를 고쳐야 할 수 있다.
- **뜨기 직전 영상**: 유튜브 검색 결과 형식에 기대고 있어서, 유튜브가 바꾸면 동작이 멈출 수 있다.
- **채널 목록**: 대체 방법('동영상' 탭)은 유튜브 채널 페이지 형식에 기대고 있다. yt-dlp를 최신 버전으로 유지해야 한다 (`uv lock --upgrade-package yt-dlp`).
