# 제작 의도

유튜브 댓글 에이전트를 왜 이렇게 만들었는지 적은 문서다. 코드가 어떻게 동작하는지는 [IMPLEMENTATION.md](IMPLEMENTATION.md)에 있다.

## 처음에 정한 것

과제의 핵심은 "AI가 댓글을 쓴다"가 아니라 **AI가 쓴 글을 그대로 믿지 않고, 규칙을 어기는 댓글은 절대 올라가지 않게 하는 것**이라고 봤다. AI는 시키는 대로 쓰다가도 글자 수를 넘기거나, 영상과 상관없는 말을 지어내거나, "사주 봤는데 맞더라" 같은 가짜 후기를 쓴다. 그래서 설계를 세 겹으로 나눴다.

1. **AI는 초안만 쓴다.** 무엇을 올릴지 판단하지 않는다.
2. **검사기가 판단한다.** AI가 쓴 글과 사람이 고친 글이 같은 검사기를 지난다.
3. **서버가 강제한다.** 화면에서 버튼을 끄는 것은 안내일 뿐이다. 게시 직전에 서버가 검사기와 운영 규칙을 다시 돌린다.

이렇게 나누면 AI 모델을 바꿔도 같은 검사기와 규칙을 지난다. Claude, Gemini, Groq 중 어느 것으로 초안을 만들어도 마찬가지다.

또 하나 정한 것은 **기본값은 안전한 쪽**이다. 과제 방식(시청자인 척하는 광고 댓글, 여러 계정)은 유튜브 스팸 정책과 표시광고법에 걸릴 수 있다. 그래서 게시 범위 기본값을 "본인 테스트 영상만"(`posting_scope: test_only`)으로 두었다. 지정 채널에 게시하려면 설정을 직접 바꿔야 한다. 설정값이 이상하면 이것도 `test_only`로 본다.

## 기능별 이유

### ① 영상 불러오기 — YouTube API 키 없이

- **왜 API 키를 안 썼나:** 심사자가 키를 만들지 않고 바로 돌려 볼 수 있게 하려고. 채널 RSS와 yt-dlp만으로 필요한 정보(제목, 자막, 인기 댓글, 채널 ID)를 다 얻을 수 있었다.
- **왜 RSS 먼저, '동영상' 탭은 나중에:** RSS는 올린 시각이 분 단위로 정확하다. 다만 가끔 404·500이 나서, 3번 다시 요청해도 안 되면 그 채널만 '동영상' 탭으로 읽는다. 탭에서 읽은 날짜는 "3일 전" 같은 표시에서 계산한 근삿값이라 화면에 "날짜 어림값"이라고 알린다. 정확하지 않은 값을 정확한 척 보여 주지 않으려고.
- **왜 한 채널 실패가 전체 실패가 아닌가:** 5개 채널을 동시에 요청하고, 실패한 채널만 이름을 알린다. 시연 중 채널 하나 때문에 화면 전체가 비면 안 되기 때문이다.
- **왜 라이브 다시보기를 빼나:** 자막이 없어서 영상 속 장면을 짚는 댓글을 쓸 수 없다.

### ② 연애 고민과 댓글 초안

- **왜 연애 고민을 먼저 정리하나:** 과제는 영상이 다루는 연애 고민에서 댓글을 시작하라고 요구한다. 고민을 한 줄로 정리한 뒤, 영상 속 구체적인 말·장면에 반응하도록 했다.
- **연애와 무관한 영상은 거절한다:** 강아지 산책처럼 연애와 관련 없는 영상에 고민을 지어내면 운명원 연결도 억지스러워진다. AI가 관련 없다고 답하면 재시도 없이 초안을 거절하고 이유를 보여 준다.
- **운명원이 어떤 곳인지 함께 적는다:** 처음 듣는 사람도 알도록 브랜드 가까이에 연애사주·연애운·궁합 같은 말을 넣는다. 직접 이용한 후기 대신 보고 싶다는 관심으로 연결한다.
- **자막이 없으면 영상을 직접 본다:** 짧은 영상(10분·20MB 이하)을 받아 Gemini에 화면과 소리를 보여 주고 장면 설명을 받는다. 실패하면 썸네일로 대신하고, 그 사실을 출처에 표시한다. 내용을 전혀 알 수 없으면 초안을 만들지 않는다.
- **왜 `detail`(영상 속 말 5~15자)을 따로 받나:** "영상을 봤다"는 증거를 코드로 확인하기 위해서다. AI가 밝힌 말이 실제 자막(또는 장면 설명)에도 있고 댓글에도 있어야 통과한다. 맥락 이해(25점)를 AI의 말이 아니라 대조로 증명한다.
- **왜 말투를 바꿨나:** 지정 채널 댓글을 살펴보니 좋아요가 많은 글은 인용 뒤에 공감을 붙이기보다 짧은 요약·반박·질문처럼 입장이 분명했다. 그래서 입장을 먼저 고르고, 짧은 근거 조각만 문장에 섞게 했다. 운명원도 긴 칭찬 대신 내 고민에 붙는 망설이는 덧말로 남긴다. 이 방식이 실제로 더 좋은지는 블라인드 비교로 확인해야 한다.
- **왜 떨어지면 이유를 붙여 다시 쓰게 하나:** "132자 (기준 40~120자)"처럼 구체적인 이유를 주면 AI가 다음 시도에서 고친다. 최대 3번까지만 하고, 그래도 안 되면 마지막 초안과 이유를 그대로 보여 준다. 사람이 고칠 수 있게 하려고.
- **왜 JSON 모드를 안 썼나:** 공급자마다 지원 여부가 달라서다. 대신 답에서 `{ … }`만 꺼내고, 못 꺼내면 다시 요청한다.

### AI 공급자 — 무료로 돌아가게

- **왜 여러 공급자를 붙였나:** 처음엔 Claude만 썼다. 심사자가 Claude 계정이나 유료 키가 없으면 초안을 만들 수 없다. 그래서 무료 등급이 있는 Gemini, Groq, OpenRouter를 붙였다. 셋 다 같은 요청 형식이라 코드 하나를 같이 쓴다.
- **왜 Gemini 3.5 Flash가 기본인가:** 무료 모델 5개를 실제 영상 11건으로 비교했다. 3.5 Flash와 3.8 Flash는 11건 모두 통과했고 품질 점수도 비슷했다. 3.5 Flash가 5배 빨라서(13.5초 대 71.7초) 기본으로 정했다.
- **왜 Groq는 대체로만 쓰나:** Gemini 무료는 하루 20회라 시연 중 한도가 찰 수 있다. 그래서 Gemini가 한도 초과(429)나 혼잡(503)일 때만 Groq로 넘긴다. Groq는 11건 모두 통과했지만 품질 점수가 3.0으로 Gemini(3.8)보다 낮아 기본으로는 쓰지 않는다. 키가 틀린 것 같은 다른 오류는 넘기지 않는다. 설정 실수를 가리지 않으려고.

### ③ 게시 — 한 글자씩, 그리고 확인까지

- **왜 한 글자씩 입력하나:** 과제 요구사항이다. 시연 영상에서 실제로 입력되는 모습이 보이도록 브라우저를 화면에 띄운다.
- **왜 "게시 버튼을 눌렀다"가 아니라 "내 댓글이 보인다"를 성공으로 보나:** 버튼을 눌러도 댓글이 안 올라갈 수 있다. 그래서 게시 후 댓글 목록에서 내 댓글 앞 18자를 찾고, 찾으면 그 댓글의 링크를 기록한다.
- **왜 `unverified`(확인 안 됨) 상태가 따로 있나:** 버튼은 눌렀는데 내 댓글이 안 보이는 경우가 있다. 새 계정 댓글은 스팸 필터에 숨겨질 수 있어서, 실제로는 올라갔을 수 있다. 이것을 "실패"로 두면 같은 영상에 다시 게시할 수 있게 된다. 그래서 따로 두고, 영상당 1개와 하루 상한에서는 게시된 것으로 센다.
- **왜 로그인을 따로 하나 (`scripts/login.py`):** 자동 조작 창에서는 구글이 로그인을 막는 경우가 있다. 그래서 로그인만 일반 크롬으로 사람이 하고, 게시는 그 프로필 폴더를 쓴다.
- **왜 ego 브라우저 방식을 더했나:** 크롬 프로필 방식은 계정마다 로그인을 따로 해야 한다. ego 브라우저(ego lite)에 이미 로그인된 계정을 쓰면 이 단계가 없다. 게시 순서와 확인 방식은 크롬 방식과 같다. 이 방식으로 본인 테스트 영상에 실제로 게시하고, 댓글이 공개된 것을 yt-dlp로 따로 확인했다 (2026-10-22).

### 브라우저 포트 — 서버와 구현 분리

서버가 브라우저 이름마다 분기하면 새 브라우저를 붙일 때마다 게시와 로그인 확인 코드를 고쳐야 한다. 그래서 `CommentPoster` 포트에 준비 확인과 게시를 묶었다. Chrome·ego 어댑터는 기존 드라이버를 사용하므로 입력과 확인 순서는 그대로다. 공통 `PostError`로 게시 후 실패 여부도 잃지 않는다.

새 브라우저는 어댑터 파일 하나를 만들고 `agent/browsers/registry.py`에 등록한다. 서버는 수정하지 않는다. 등록되지 않은 설정 이름은 Chrome으로 조용히 바꾸지 않고 오류로 알린다. 테스트에서는 팩터리에 가짜 게시자를 넣어 실제 브라우저 없이 서버 동작을 확인한다.

### 운영 규칙 — 서버가 강제

- **허용 채널:** 화면이 보낸 채널 정보를 믿지 않는다. 서버가 yt-dlp로 받은 채널 ID로만 판단한다. 요청을 조작해도 허용 밖 채널에 게시할 수 없다.
- **영상당 1개:** 계정과 상관없이 센다. 계정을 바꿔 같은 영상에 또 다는 것을 막기 위해서다. 영상 ID는 11자리 형식만 받는다. `ID&t=1`처럼 뒤에 무언가 붙여 다른 영상인 척하는 우회가 레드팀 검토에서 통과했기 때문이다.
- **하루 10개:** "오늘"은 한국 시간 기준이다. 서버 시간대가 달라도 자정 기준이 흔들리지 않게 했다.
- **로그인된 계정만 자동 배정:** 로그인 안 된 계정이 배정되어 시연 중 실패하는 일을 막는다.
- **동시 게시 막기:** 게시 요청이 오면 검사를 시작하기 전에 "게시 중"으로 잠근다. 두 요청이 동시에 검사를 통과해 같은 영상에 두 번 게시되는 것을 막는다.

### 기록

- **왜 SQLite 파일 하나인가:** 설치할 것이 없고, 서버를 껐다 켜도 규칙이 유지된다. 규칙 검사("이 영상에 성공이 있나", "오늘 몇 개인가")도 같은 표를 조회한다.
- **왜 차단도 기록하나:** 과제 요구사항이다. 그리고 "규칙이 실제로 동작했다"는 증거가 된다.
- **왜 실패 순간을 캡처하나:** "댓글창을 못 찾음" 같은 실패는 글만으로는 원인을 알기 어렵다. 그 순간 화면이 있으면 바로 알 수 있다.

### 화면

- **왜 세 칸인가:** 과제 흐름(① 불러오기 → ② 선택 → ③ 게시)을 그대로 화면에 옮겼다. 칸마다 "완료 / 지금 / 대기"를 표시해 지금 어느 단계인지 알 수 있다.
- **왜 규칙 검사표를 보여 주나:** "왜 게시 버튼이 꺼졌는지"를 사용자가 바로 알게 하려고. 실패 이유는 ✕ 표시와 함께 글로 적는다. 색만으로 구분하지 않는다.
- **왜 빌드 도구 없이 만들었나:** 서버만 켜면 바로 열린다. 심사자가 `npm install` 같은 단계를 거칠 필요가 없다.
- **사용자 검토에서 고친 것:** 게시 중에 다른 영상을 고르면 결과가 엉뚱한 영상에 붙는 문제, 늦게 온 옛 검사 결과가 새 결과를 덮어쓰는 문제 등 8건을 고쳤다.

### 보안

내 컴퓨터에서만 쓰는 도구지만, 계정으로 실제 게시를 하므로 몇 가지는 막았다.

- 서버는 `127.0.0.1`에서만 열린다. 같은 와이파이의 다른 기기는 접속할 수 없다.
- 다른 웹사이트가 내 브라우저를 통해 대시보드에 요청을 보내는 것(DNS 리바인딩)을 `Host`·`Origin` 확인으로 막는다.

## 검증 방법

- **자동 테스트.** 검사기, 운영 규칙, AI 연결, 서버 API, 게시 결과 처리를 외부 서비스 없이 확인한다.
- **레드팀 검토 (2026-10-20).** 다른 AI에게 "규칙을 우회해 보라"고 맡겼다. 우회 7건이 나왔고, 각각을 테스트로 만든 뒤 고쳤다. 이 19개 테스트 중 18개는 고치기 전 코드에서 실패한다. 고친 효과를 테스트로 증명하기 위해서다.
- **실제 영상으로 확인.** 무료 모델 비교에 실제 영상 11건을 썼고, 본인 테스트 영상에 실제로 게시했다.

## 버린 시도

| 시도                  | 버린 이유                                                                                                                                                            |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node.js 서버          | yt-dlp가 Python 프로그램이라 외부 프로그램으로 실행해야 했다. FastAPI로 옮기니 코드에서 바로 부를 수 있었다. API 주소와 응답 모양은 그대로 두어 화면은 바꾸지 않았다 |
| YouTube Data API      | 심사자가 키를 만들어야 한다. RSS와 yt-dlp로 충분했다                                                                                                                 |
| Ollama 같은 로컬 모델 | 컴퓨터마다 속도가 크게 다르고 모델 파일(약 8GB)을 받아야 한다. "바로 실행해 보기"에 맞지 않았다                                                                      |
| Gemini Flash-Lite     | 3.1은 다시 써 달라고 해도 매번 120자를 넘겼다. 3.5는 9건 중 7건에 같은 끝 문장을 썼다                                                                                |
| Gemma 4 (OpenRouter)  | 답 앞에 생각 과정을 붙여서 JSON을 꺼내지 못했다                                                                                                                      |
| 게시 버튼 클릭 = 성공 | 실제로 올라갔는지 알 수 없다. 내 댓글이 보여야 성공으로 바꿨다                                                                                                       |
| 화면에서만 규칙 막기  | 요청을 직접 보내면 우회된다. 서버에서 다시 검사하게 바꿨다                                                                                                           |
| 서킷 브레이커         | 버튼 한 번에 요청이 5번뿐이라 보호할 부담이 없었다. 자동으로 자주 돌리게 되면 넣을 자리는 정해 두었다                                                                |

## 한계

- 크롬 프로필 방식(`poster.py`)은 ego 방식과 같은 순서로 동작하지만 실제 게시는 아직 해 보지 않았다.
- 유튜브 화면 구조가 바뀌면 댓글창·게시 버튼 선택자를 고쳐야 한다.
- 새 계정 댓글은 스팸 필터에 숨겨질 수 있다. "내 화면에서 보임"이 확인 기준이라 다른 사람에게도 보이는지는 보장하지 않는다.
